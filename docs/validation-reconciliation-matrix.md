Prisma, and API behavior. Shared schemas describe serializable API input; services
retain business rules and authorization.

## Classified Conflicts

- **A Agreement:** shared enum and core request shapes for jobs, messages, admin, and support text.
- **B Frontend-only UX:** character counters, required category selection in the support UI, password confirmation, file objects, and focus behavior.
- **C Backend-only business rule:** future job deadlines, duplicate applications, profile ownership, participant checks, approval state, and CV requirements based on profile mode.
- **D API contract difference:** multipart application coercion and the former JobForm question field names; adapters now normalize these at the boundary.
- **E Optional/nullable difference:** profile end dates/descriptions are nullable at persistence and normalized at frontend API boundaries.
- **F Legacy duplication:** frontend and backend profile schemas now re-export canonical package schemas.
- **G Domain difference:** skill character restrictions and password policy remain unresolved because current behavior conflicts without an authoritative product rule.

## Unresolved / Needs Business Decision

1. Should password minimum be 6 or 8 for all authentication requests?
2. Should submitted birthdate be required and persisted, replacing the Prisma `now()` default behavior?
3. Should skill names allow symbols used by real technologies, such as `C++`, `.NET`, and `C#`?
4. Should support category be mandatory at the API level or only in the current UI?
5. Should a non-professional application require a CV upload as a shared input rule or remain a service/business rule?

These are the only unresolved validation conflicts identified by the current code audit.
